# 头像发布与验收

部署前先执行 `supabase/20261105_avatar_lifecycle.sql`，再执行 `supabase/20261116_avatar_webp.sql`。迁移不删除已有对象；它设置头像列表/删除权限、64 个对象的每用户配额，以及头像引用存在性校验。头像存储桶只存 WebP，以减小体积：新版本只接受编辑器导出的 256×256 WebP，第二个迁移让上传校验接受 `.webp` 文件名（第一个迁移写的是 `.png`，会拒绝所有新头像）。旧客户端的固定文件覆盖被禁用。迁移与前后端代码应在同一发布窗口上线，回滚需配套恢复原上传策略。

预览和保存均从相同裁切 canvas 输出 256×256 WebP（质量 0.82，一般只有几 KB），预览与保存使用相同的编码，看到的就是保存的效果。页面直接上传该 File，不再二次缩小或压缩。没有 WebP 编码能力的浏览器（`toBlob` 会改给 PNG）会提示无法生成 WebP，不会上传 PNG。服务端无法解码 WebP，改为校验 RIFF/WebP 结构：单张静态图、位流头里的尺寸正好 256×256、没有越界或多余的数据块；保存失败重试复用 File 和已经上传的 URL。对象以用户 ID 加 SHA-256 命名，相同图片重试不会累积新对象。

重试相同头像时直接复用已有对象。上传新头像时，只在发现超过 7 天的对象后读取当前头像并尝试清理。未满配额时清理失败仍可上传，达到配额时须确认清理实际释放了空间。数据库策略与 profile 更新使用同一用户锁，阻止正在使用的头像被删除，阻止 profile 引用已删除对象。7 天保留期用于缓存、重试和回滚；64 个配额限制连续换图产生的对象数量。闲置账号的历史图片不会主动被扫描，但对象数量受配额约束。不要绕过 Storage API 直接删除 storage.objects 元数据。

本次迁移使用本地自动化测试验证头像编码校验、上传重试、清理筛选、配额处理和页面状态。未在本次工作中执行数据库迁移，未完成真实 Supabase Storage 或多连接锁竞争验收。真实部署需检查不存在其他宽松的 Storage 策略，并验证多个客户端并发保存/清理、Storage API 冲突状态和真实 RLS。

人工验收：使用有清晰边界和方向标记的图片，分别测试拖动、缩放、90°旋转，比较大预览、小预览和保存后头像；刷新页面后再次比较。测试失败重试、取消与重新选图、手机竖屏/横屏、键盘 Escape 和焦点恢复。头像在不同显示尺寸下会进行显示缩放，像素级匹配应比较实际 256×256 导出图。

RV 适配：头像入口位于个人资料弹窗，保留昵称保存与官方账号显示逻辑。Vercel 构建须包含 vendor/ 下的 Cropper 文件。两个部署使用同一数据库时，迁移只需执行一次。

如果弹窗显示「权限不足」，先确认 `supabase/20261116_avatar_webp.sql` 已经执行。如果显示「存储桶不接受这种图片格式」或「超过存储桶的大小上限」，核对 `avatars` 桶允许 `image/webp`，大小上限不低于 1 MB。如果弹窗显示存储桶不存在或权限不足，维护者应在业务 Supabase 项目核对公开的 `avatars` 桶、WebP 上传限制，以及 `20261105_avatar_lifecycle.sql` 的读写策略。存储认证失败时检查部署端业务签名密钥与该 Supabase 项目是否匹配。资料更新返回 HTTP 409 时，检查该用户的 `business_users` 行是否存在并可由本人更新。
